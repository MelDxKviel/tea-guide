# Tea Guide — техническое задание на разработку

Ты — senior frontend/product engineer и одновременно аккуратный исследователь чайной тематики. Твоя задача — спроектировать и реализовать production-ready статический сайт **Tea Guide**.

Не относись к этому как к задаче «сгенерировать красивый лендинг про чай». Это **функциональный продукт**, где главным пользовательским сценарием является удобное заваривание китайского чая проливами с автоматически подготовленной последовательностью таймеров.

Истории, статьи, каталог, информация о происхождении и посуде важны, но являются вторичными относительно brewing-функциональности.

Проект должен быть пригоден для реального использования, дальнейшего наполнения сотнями чаёв, SEO-продвижения и последующего добавления других языков.

---

# 1. Главная идея продукта

Tea Guide должен отвечать на практический вопрос:

> «У меня есть конкретный чай. Сколько граммов взять, какую температуру воды использовать и сколько секунд держать каждый пролив?»

Пользователь выбирает конкретный чай, посуду и объём, после чего сайт:

1. берёт проверенный рецепт именно этого чая;
2. рассчитывает необходимую граммовку под объём пользователя;
3. показывает температуру воды;
4. при необходимости проводит через промывку;
5. автоматически подготавливает таймер первого пролива;
6. после его завершения подготавливает следующий;
7. пользователь сам запускает каждый следующий пролив;
8. сайт автоматически знает длительность всех последующих проливов.

Пользователь **не должен вручную помнить последовательность**:

`8 → 10 → 15 → 20 → 30 → 45 → 60 секунд`

Именно автоматическое проведение через всё чаепитие является основной killer feature продукта.

# 2. Приоритеты разработки

Приоритеты строго следующие:

## P0 — brewing engine

В первую очередь реализовать:

- модель рецептов;
- разные рецепты для разных чаёв;
- разные рецепты для разной посуды;
- расчёт граммовки;
- настройку крепости;
- последовательность проливов;
- state machine таймера;
- правильный отсчёт времени;
- промывку;
- звук;
- вибрацию;
- Wake Lock;
- сохранение активного чаепития;
- восстановление после перезагрузки страницы;
- mobile-first интерфейс таймера.

## P1 — каталог и страницы чаёв

После рабочего brewing engine:

- главная;
- каталог;
- категории;
- подкатегории;
- страницы конкретных чаёв;
- рекомендации по посуде;
- способы заваривания;
- статьи.

## P2 — качественный чайный контент

После того как функциональная часть работает:

- исследовать китайские источники;
- заполнить стартовый каталог;
- добавить источники;
- добавить исторические и практические материалы.

## P3 — SEO, PWA, polish

SEO-фундамент должен закладываться сразу архитектурно, однако окончательная оптимизация проводится после основных страниц.

# 7. Главная сущность продукта — BrewingRecipe

**Запрещено** создавать один универсальный рецепт на категорию чая.

Нельзя писать:

> «Все улуны завариваются 7 г / 100 мл».

Каждая конкретная чайная позиция имеет **собственные проверенные параметры**.

Например:

```text
Да Хун Пао
Гайвань
8 г / 110 мл
95°C
8 / 10 / 15 / 20 / 30 / 45 / 60...
```

Те Гуань Инь может иметь совершенно другую последовательность.

Лунцзин — другую.

Шу Пуэр — другую.

# 8. Китайские источники — обязательное требование

Информация о рецептах не должна генерироваться из общих знаний LLM.

Для каждого конкретного чая выполнить исследование.

Приоритет источников:

## Tier 1

- государственные китайские ресурсы;
- национальные или отраслевые стандарты;
- китайские научно-исследовательские чайные институты;
- профильные университеты;
- 中国茶叶流通协会;
- 中国农业科学院茶叶研究所;
- другие авторитетные китайские исследовательские/отраслевые организации.

## Tier 2

- официальные сайты регионов происхождения;
- региональные чайные ассоциации;
- организации, связанные с geographical indication;
- официальные организации соответствующей чайной зоны.

## Tier 3

Авторитетные китайские специализированные чайные источники.

## Tier 4

Крупные китайские производители конкретного чая.

Использовать их прежде всего для практической техники гунфу, если более первичные источники не дают точных секунд.

## Tier 5

Другие качественные источники можно использовать как вспомогательные.

# 9. Правила исследования brewing recipe

Для каждой чайной позиции:

1. определить корректное китайское название;
2. определить пиньинь;
3. определить корректную чайную категорию;
4. определить регион происхождения;
5. найти китайские источники;
6. исследовать соотношение листа и воды;
7. исследовать рекомендуемую температуру;
8. исследовать подходящую посуду;
9. исследовать необходимость промывки;
10. исследовать время промывки;
11. исследовать последовательность проливов;
12. сравнить несколько источников;
13. выбрать usable baseline recipe;
14. сохранить источники;
15. указать, какие именно параметры подтверждает каждый источник.

Если источники расходятся — **не выдавать спорный параметр за объективный стандарт**.

Если официальный источник говорит только:

```text
8 г
100 мл
95°C
```

но не предоставляет последовательность проливов, нельзя придумывать секунды самостоятельно.

Нужно дополнительно исследовать практические китайские источники.

# 10. Источники рецептов

Каждый BrewingRecipe должен иметь собственные источники.

Недостаточно иметь три ссылки только в общей статье о чае.

Например:

```yaml
sources:
  - sourceId: example-source-1
    supports:
      - leaf_ratio
      - temperature

  - sourceId: example-source-2
    supports:
      - rinse
      - infusion_times
```

Допустимые значения `supports`:

```text
leaf_ratio
water_volume
temperature
rinse
infusion_times
vessel
western_method
thermos_method
cold_brew_method
origin
history
taste
roasting
```

# 11. Internal confidence

Добавить внутренний editorial quality flag:

```ts
type RecipeConfidence = 'high' | 'medium';
```

Он не обязан отображаться обычному пользователю.

`high`:

есть хорошие согласующиеся китайские источники.

`medium`:

базовые параметры подтверждены, но последовательность проливов была собрана из нескольких практических источников.

Не создавать `low` production-рецепты.

Если информации недостаточно — лучше не добавлять рецепт.

---

# 12. Методы приготовления

Поддержать:

```ts
type BrewingMethod =
  | 'gongfu'
  | 'western'
  | 'thermos'
  | 'cold_brew';
```

Но не каждый чай обязан иметь все методы.

Например:

```text
Да Хун Пао
✓ gongfu
✓ western
— thermos
— cold brew
```

или:

```text
Шу Пуэр
✓ gongfu
✓ western
✓ thermos
```

Cold brew добавлять только для чаёв, для которых он действительно является разумным способом приготовления.

Термос аналогично.

---

# 13. Посуда

Основные варианты для гунфу:

```text
Гайвань
Исинский чайник
```

Гайвань считать наиболее универсальным вариантом и обычно использовать как default.

Но набор доступной посуды определяется конкретным рецептом.

Не надо создавать огромный бессмысленный selector:

```text
фарфор
стекло
керамика
глина
серебро
чайник
типот
колба
...
```

если для продукта это не требуется.

Отдельно поддерживать `thermos` для соответствующих методов.

# 20. Расчёт граммовки

Расчёт выполняется относительно конкретного BrewingRecipe.

Например рецепт:

```text
8 г / 110 мл
```

Пользователь выбрал:

```text
135 мл
```

Внутренне:

```ts
calculatedGrams =
  referenceLeafGrams *
  userVolumeMl /
  referenceVolumeMl;
```

Не использовать универсальный коэффициент категории чая.

---

# 21. Округление граммовки

Пользователь не должен получать:

```text
9.818181818 г
```

Хранить точное расчётное значение, но отображать практичное.

Предпочтительный шаг:

```text
0.5 г
```

Пример:

```text
Расчёт: 9.82 г
UI: 10 г
```

или:

```text
Расчёт: 9.31 г
UI: 9.5 г
```

Если исследование UX покажет более естественную стратегию округления — допускается улучшить её.


```ts

```

Крепость по умолчанию изменяет **только граммовку**.

Она не должна автоматически изменять:

- температуру;
- rinse;
- все секунды проливов;
- количество проливов.

Иначе получается неоправданная псевдоточность.

# 25. Таймер — главный UI продукта

Визуальный дизайн может отличаться.

Ключевые требования:

- общее количество;
- текущее время;

# 26. Каждый пролив запускается вручную

Критически важно:

**следующий пролив никогда не запускается автоматически.**

После окончания:

```text
Пролив готов
```

Сигнал.

Вибрация.

Далее:

```text
Следующий пролив — 20 секунд

[ НАЧАТЬ СЛЕДУЮЩИЙ ]
```

Человек может пить чай сколько угодно.

Сайт не отсчитывает паузу между проливами.

# 27. Timer state machine

Не реализовывать таймер как хаотичный набор boolean-переменных.

Создать явную state machine либо эквивалентную строгую модель состояний.

Минимальные состояния:

```ts
type TimerState =
  | 'setup'
  | 'rinse-ready'
  | 'rinse-running'
  | 'rinse-paused'
  | 'rinse-complete'
  | 'infusion-ready'
  | 'infusion-running'
  | 'infusion-paused'
  | 'infusion-complete'
  | 'session-complete';
```

Переходы должны быть детерминированными и тестируемыми.

---

# 28. Правильный отсчёт времени

**Запрещено** считать время простой схемой:

```ts
setInterval(() => remaining--, 1000);
```

Browser background throttling делает такой подход ненадёжным.

При старте сохранять:

```ts
startedAt
durationMs
expectedEndAt
```

Оставшееся время:

```ts
Math.max(
  0,
  expectedEndAt - Date.now()
)
```

`requestAnimationFrame` / `setInterval` используются только для обновления UI.

Источник истины — timestamps.

После:

- background;
- lock screen;
- смены вкладки;
- lag;
- temporary freeze;

таймер должен показывать корректное реальное время.

---

# 29. Пауза

При pause сохранить фактическое `remainingMs`.

При resume создать новый:

```text
expectedEndAt =
  Date.now() + remainingMs
```

Пауза не должна ломаться после нескольких циклов pause/resume.


# 31. Изменение времени вручную


Source recipe не изменяется.

При следующем новом чаепитии используется исходный verified recipe.

# 33. Завершение пролива

- проигрывается звук, если включён;
- вызывается вибрация, если включена и поддерживается;
- показывается текстовое сообщение.

Например:

**Готово — сливайте чай**

Нельзя полагаться только на изменение цвета.

Не делать коллекцию из:

- флейты;
- тибетских чаш;
- «дзен-звуков».

Не скатываться в тематический китч.

# 35. Вибрация

Настройка:

```text
Вибрация
ON / OFF
```

- приложение продолжает работать;
- не показывать техническую ошибку;
- можно скрыть unsupported control или корректно disabled.

Настройка сохраняется локально.

# 36. Wake Lock

Во время brewing session по возможности использовать Screen Wake Lock API.

Настройка:

```text
Не выключать экран во время чаепития
ON / OFF
```

Default:

```text
ON
```

Если API недоступен — graceful degradation.

Wake Lock не должен быть обязательным условием работы приложения.

При возврате document visibility в foreground при необходимости корректно получать lock повторно.

Режим таймера должен ощущаться как аккуратное специализированное приложение.

Общий дизайн:

- современный;
- необычный;
- человеческий;
- спокойный;
- тактильный;
- выразительный;
- без визуального шума;
- без ощущения SaaS-template;
- без ощущения AI-generated website.

---

# 64. Критически важно: NO AI SLOP

Интерфейс не должен выглядеть так, будто его за 20 секунд сгенерировала нейросеть.

Запрещены типичные AI-design паттерны без функциональной причины:

- сине-фиолетовые градиенты;
- glowing CTA;
- glassmorphism повсюду;
- blob backgrounds;
- случайные abstract gradients;
- одинаковые огромные rounded cards на каждом экране;
- всё с `border-radius: 24px`;
- десятки pill-компонентов;
- бессмысленные floating cards;
- giant marketing hero;
- fake statistics;
- fake testimonials;
- «10 000 tea lovers»;
- «discover the art of tea»;
- sparkle icons;
- emoji как системные иконки;
- декоративные иероглифы, не имеющие отношения к конкретному тексту;
- псевдовосточный китч;
- золотые драконы;
- бамбук ради бамбука;
- красно-золотая «китайская» тема;
- дзен-камни;
- бесконечные изображения гор;
- бессодержательные marketing copy.

---

# 65. Характер визуального дизайна

Нужно добиться ощущения:

> «Этот интерфейс кто-то действительно спроектировал для людей, которые заваривают чай».

Допустимы:

- интересная editorial typography;
- асимметрия;
- хорошие отступы;
- контраст масштаба;
- выразительные фотографии чайного листа;
- фотографии посуды;
- тонкая визуальная связь с бумажными чайными карточками/этикетками;
- лёгкая тактильность;
- индивидуальные details.

Но ничего не должно мешать функциональности.

---

# 66. Цвет

Не требуется буквально использовать бежево-коричневую «чайную палитру».

Создать полноценную палитру:

- background;
- elevated surface;
- primary text;
- secondary text;
- subtle border;
- accent;
- positive/complete;
- warning/error.

Цвета должны иметь хороший контраст.

Не использовать gradient как основной способ сделать интерфейс «интересным».

---

# 67. Типографика

Типографика играет большую роль.

Нужна заметная разница между:

- editorial headings;
- UI controls;
- numeric timer;
- metadata;
- body text.

Особенно внимательно подобрать отображение:

```text
00:15
```

Timer digits не должны прыгать по ширине.

Использовать tabular numerals.

Китайские символы должны отображаться корректно.

Не подключать огромные font bundles без необходимости.

---

# 68. Responsive / mobile-first

Главное устройство — смартфон.

Особенно таймер.

Primary controls должны:

- удобно нажиматься большим пальцем;
- иметь нормальные touch target;
- не быть слишком близко друг к другу;
- не требовать hover.

Desktop должен выглядеть полноценно, а не как растянутый мобильный экран.

---

# 69. Timer mobile UX

Во время активного чаепития secondary navigation можно визуально приглушить.

Пользователь должен видеть прежде всего:

```text
чай
номер пролива
таймер
главную кнопку
±5
progress
```

Не показывать в одном viewport историю, breadcrumbs и большой footer.

---

# 70. Desktop keyboard shortcuts

Допустимо реализовать:

```text
Space → start / pause
+ → +5 секунд
- → −5 секунд
Right Arrow → следующий этап
```

Только если shortcut не конфликтует с обычной navigation/input.

Сделать discoverable через help/tooltip, но не перегружать UI.

---

# 71. Accessibility

Минимум:

- semantic HTML;
- настоящие `<button>`;
- настоящие `<nav>`;
- правильная heading hierarchy;
- keyboard navigation;
- visible focus;
- accessible labels;
- достаточный contrast;
- `prefers-reduced-motion`;
- состояние не сообщается только цветом;
- timer status доступен assistive technologies;
- icon-only buttons имеют aria-label;
- touch targets адекватного размера.

Анимации не должны быть обязательными для понимания интерфейса.

# 72. SEO — фундаментальная часть архитектуры

Сайт должен быть SEO-ready с первого релиза.

Но SEO не должно ухудшать читаемость.

Никакого keyword stuffing.

# 73. Static HTML

Страницы чаёв должны существовать как полноценный статически сгенерированный HTML.

Поисковику не должен требоваться client-side JavaScript, чтобы увидеть:

- название;
- китайское название;
- описание;
- рецепт;
- температуру;
- граммовку;
- историю;
- ссылки.

Интерактивный calculator/timer является enhancement.

---

# 74. SEO metadata

Для каждой индексируемой страницы:

- unique `<title>`;
- meta description;
- canonical;
- Open Graph;
- Twitter/social metadata при необходимости;
- правильный language;
- preview image, если доступно.

Tea content должен иметь собственные SEO-поля либо генерироваться по корректному template с возможностью override.

# 75. Sitemap

Автоматически генерировать sitemap.

Он должен включать:

- teas;
- categories;
- subcategories;
- teaware;
- guides.

Не включать технические/client-only URL.

---

# 76. robots.txt

Добавить корректный robots.txt.

Не запрещать индексирование production content.

---

# 77. Structured data

Использовать JSON-LD только там, где schema действительно соответствует содержимому.

Не размечать страницу фиктивными типами ради SEO.

Можно рассмотреть:

- BreadcrumbList;
- Article для содержательных материалов;
- подходящие общие WebPage types.

Не использовать Recipe schema автоматически для чая, если содержание не соответствует семантике пищевого Recipe schema.

---

# 78. Breadcrumbs

Например:

```text
Чаи → Улуны → Уишаньские → Да Хун Пао
```

Breadcrumbs:

- помогают navigation;
- создают internal linking;
- могут использоваться в structured data.

На mobile отображать компактно.

# 79. Internal linking

Страница Да Хун Пао должна естественно ссылаться на:

- улуны;
- уишаньские улуны;
- гайвань;
- исинский чайник;
- статью про проливы;
- связанные чаи.

Не создавать отдельные бессмысленные SEO link blocks.

# 80. SEO intent страницы чая

Структура страницы должна естественно отвечать запросам вроде:

```text
да хун пао

да хун пао сколько грамм
да хун пао температура
да хун пао проливы
да хун пао сколько секунд

```

Не писать отдельный paragraph для каждого keyword.

Правильно структурированный полезный контент должен покрывать intent сам.

# 81. URL и будущая локализация

Сейчас default Russian URL:

```text
/tea/da-hong-pao/
```

Не делать сейчас:

```text
/ru/tea/da-hong-pao/
```

Архитектура должна позволить в будущем:

```text
/en/tea/da-hong-pao/
```

Default locale — русский без prefix.

# 82. i18n readiness

Хотя сейчас существует только русский язык, UI-строки нельзя хаотично hardcode по компонентам.

Создать i18n abstraction.

Например:

```text
timer.start

timer.resume
timer.nextInfusion
timer.complete
brew.strength.soft
brew.strength.normal
brew.strength.strong
brew.vessel.gaiwan
```

Сейчас словарь только `ru`.

# 83. Контент и i18n

Стабильные identifiers не должны зависеть от языка.

Например:

```text
teaId: da-hong-pao
```

остаётся одинаковым.

Localized content должен быть отделяемым.

Архитектура должна позволять в будущем добавить:

```text
ru
en
zh
```

без переписывания brewing engine.

Сами числовые recipes не нужно дублировать на каждый язык.

# 85. Форматы данных

Предпочтительно:

### Articles/content

Markdown / MDX / Astro Content Collections.

### Recipes

YAML или другой человекочитаемый structured format.

Например:

```yaml
id: da-hong-pao-gongfu-gaiwan

teaId: da-hong-pao

method: gongfu
vessel: gaiwan

referenceVolumeMl: 110
referenceLeafGrams: 8

temperature:
  recommendedCelsius: 95

rinse:
  durationSeconds: 5
  optional: true

infusions:
  - number: 1
    durationSeconds: 8

  - number: 2
    durationSeconds: 10

  - number: 3
    durationSeconds: 15
```

Это только пример структуры.

**Не воспринимать приведённые числа как достоверный рецепт Да Хун Пао. Перед production наполнением исследовать китайские источники.**

---

# 86. Schema validation

Build должен падать при некорректных данных.

Проверять:

- уникальность ids;
- уникальность slug;
- существование referenced tea;
- существование referenced source;
- volume > 0;
- grams > 0;
- temperature в разумном диапазоне;
- infusion duration > 0;
- infusion numbers последовательны;
- gongfu имеет `infusions`;
- cold brew имеет соответствующий duration;
- referenced subgroup существует;
- locale content существует;
- source URL валиден.

---

# 87. Referential integrity

Нельзя получить production build, где:

```text
recipe.teaId = foo
```

а чая `foo` нет.

Или:

```text
sourceId = chinese-source-27
```

а такого source нет.

Добавить validation script/build validation.

- есть ли пиньинь;
- есть ли хотя бы один recipe;
- есть ли источники recipe;
- есть ли SEO title/description.

# 89. Изображения

Использовать реальные качественные изображения:

- сухого чайного листа;
- настоя;
- региона при необходимости;
- посуды.

Не генерировать AI-art в качестве основного контента без явной необходимости.

Не использовать фотографии просто как decorative filler.

Оптимизировать:

- responsive sizes;
- modern formats;
- lazy loading;
- explicit width/height;
- предотвращение CLS.

Hero конкретного чая может быть визуально выразительным, но не должен отодвигать кнопку «Заварить» далеко вниз.

---

# 90. Performance

Сайт должен быть быстрым на мобильных устройствах.

Цели:

- минимум client JS;
- lazy-load необязательного;
- оптимизированные изображения;
- отсутствие тяжёлых animation libraries без причины;
- отсутствие giant component library без необходимости;
- отсутствие сторонней аналитики на первой версии, если она не нужна;
- отсутствие webfonts размером в несколько мегабайт.

Core Web Vitals учитывать как quality criterion.

---

# 91. Animations

Использовать только meaningful animations:

- плавное изменение состояния таймера;
- небольшой feedback на завершение;
- раскрытие sheet;
- progress transitions.

Не анимировать всё подряд.

Учитывать:

```css
prefers-reduced-motion
```

---

# 92. Error handling

UI не должен разваливаться при:

- unsupported vibration;
- unsupported Wake Lock;
- denied Wake Lock;
- unavailable service worker;
- corrupted localStorage;
- старая версия stored BrewSession;
- отсутствующий optional image;
- offline navigation;
- invalid custom volume.

Нужен graceful degradation.

---

# 93. localStorage migration

Stored data versioned.

Например:

```ts
{
  version: 1,
  ...
}
```

Если формат изменён в будущем:

- мигрировать;
- либо корректно сбросить несовместимое состояние.

Не ловить приложение в permanent crash из-за старого JSON.

- next infusion;
- last infusion;
- extension.

## Persistence

- save;
- restore;
- expired timer restore;
- corrupted storage.

# 107. Copywriting

# 108. История и легенды

```text
По распространённой легенде...
```

```text
детоксицирует

очищает организм
```

без высококачественной доказательной базы.

Tea Guide прежде всего про чай и заваривание.

Не делать псевдомедицинский портал.

---

# 110. «Эффект чая»

Если упоминается характер ощущения, формулировать осторожно и субъективно.

Например:

```text
Многие воспринимают этот чай как...
```

Но этот раздел вообще не является обязательным.

Не использовать эзотерическое `чайное состояние` как псевдонаучный факт.

---

# 111. Search engine + humans

При конфликте:

```text
SEO-текст
vs
удобство человека
```

приоритет человеку.

Но хорошая информационная архитектура должна позволять иметь оба.

---

# 112. Архитектурный принцип

Разделить:

```text
domain logic
UI
content
storage
research/source data
```

Brewing engine не должен быть размазан по Astro components.

Например:

```text
lib/brewing/calculateLeafAmount.ts
lib/brewing/timer.ts
lib/brewing/session.ts
lib/brewing/recipe.ts
```

Названия могут отличаться.

Логика должна быть unit-testable без браузера, насколько это возможно.

---

# 113. Progressive enhancement

Основной principle:

```text
content = static
brewing interaction = enhanced
```

Если client JS по какой-то причине не загрузился, пользователь всё равно должен увидеть статический рецепт:

```text
8 г / 110 мл
95°C
1: ...
2: ...
```

Он потеряет интерактивный timer, но не всю информацию.

---

# 114. SEO-friendly recipe fallback

На странице всегда отображать текстовый recipe summary.

Например:

```text
Базовый рецепт

8 г / 110 мл
95°C

Проливы:
1 — 8 сек
2 — 10 сек
3 — 15 сек
...
```

И ниже/рядом:

**Запустить таймер**

Таким образом recipe индексируется и полезен даже без JS.

---

# 115. Исинский чайник

Не делать вид, что использование исинского чайника автоматически требует другого рецепта.

Если найден отдельный проверенный recipe — использовать его.

Если отличие не подтверждено, можно использовать тот же baseline ratio, но это должно быть осознанное editorial решение.

Не генерировать искусственные различия ради наличия двух кнопок.

---

# 116. Brewing recipes vs teas

Один Tea может иметь:

```text
1...N recipes
```

Например:

```text
da-hong-pao
├── gongfu-gaiwan
├── gongfu-yixing
└── western
```

Timer запускается не по Tea, а по конкретному BrewingRecipe.

---

# 117. Stable identifiers

IDs стабильны и не зависят от русского текста.

Например:

```text
da-hong-pao
da-hong-pao-gongfu-gaiwan
wuyi-rock-tea
```

Переименование display text не должно ломать references.

---

# 118. Не создавать автоматическое изменение infusion times от объёма

Пользователь меняет объём:

```text
100 → 120 мл
```

Автоматически пересчитывать граммовку.

Не пересчитывать секунды простым коэффициентом.

Последовательность infusion times является частью verified recipe.

Если в будущем будет разработана отдельная обоснованная модель адаптации — её можно добавить.

Сейчас не надо.

---

# 119. Strength тоже не меняет секунды

Повторно: `Мягче / Стандарт / Крепче` изменяет leaf amount.

Не:

```text
+15% листа
+15% времени
```

одновременно.

---

# 120. Рецепт — рекомендация, а не абсолютная истина

В интерфейсе аккуратно дать понять:

> Это базовый рецепт. Вкус можно корректировать временем следующих проливов.

Но не надо каждый раз показывать disclaimer.

Для этого и существуют `±5 сек`.

---

# 121. Page transitions / routing

Не использовать сложный client router без необходимости.

Обычная Astro navigation достаточно хороша.

Timer route/state должен быть продуман так, чтобы accidental Back не уничтожил session молча.

При попытке уйти во время active timer можно:

- сохранить session автоматически;
- не блокировать пользователя раздражающим confirmation dialog без необходимости.

---

# 122. Текущее чаепитие из любой страницы

Если есть active session, можно показывать компактный persistent affordance:

```text
Да Хун Пао · пролив 4

Продолжить
```

Например небольшой элемент в header/mobile interface.

Не делать навязчивую floating neon button.

---

# 123. Assets / source copyright

При подборе изображений учитывать права использования.

Не скачивать случайные copyrighted фотографии из Google Images в production repository.

Использовать:

- собственные;
- public domain;
- подходящую открытую лицензию;
- официально разрешённые assets.

Хранить attribution, если лицензия этого требует.

---

# 124. Privacy

Так как backend отсутствует, пользовательские brewing settings остаются локально.

Не подключать ненужные trackers.

Если analytics не требуется для MVP — не добавлять.

---

# 125. Security

Не использовать unsafe HTML из arbitrary external content.

Markdown content находится в trusted repository, но всё равно избегать ненужного raw HTML.

External links к источникам:

- безопасны;
- корректно оформлены;
- при `target="_blank"` использовать необходимые `rel`.

PWA/service worker не должен перехватывать navigation таким образом, что после обновления deploy пользователь навсегда остаётся на старой версии.

---

# 126. Первый этап реализации

Сначала создать vertical slice только на нескольких test teas.

Например:

- Да Хун Пао;
- Те Гуань Инь;
- Шу Пуэр.

Но числа recipe перед production использованием обязательно исследовать.

Vertical slice должен содержать весь flow:

```text
главная
→ чай
→ настройка
→ calculator
→ rinse
→ timer
→ next infusion
→ finish
→ recovery
```

---

# 127. После vertical slice

Только после проверки UX:

- расширить data model;
- заполнить остальные чаи;
- делать большое количество content pages.

Не клонировать недоделанный component 30 раз.

---

# 128. Research before content generation

Не начинай работу с генерации 30 длинных статей.

Сначала функциональность.

После этого для каждого tea выполнять отдельное исследование.

Если доступен web research — использовать его.

Предпочитать запросы на китайском.

Хранить source URLs и дату обращения.

---

# 129. Не выдавать примерные числа из этого ТЗ за фактические recipes

Все встречающиеся в ТЗ числа вроде:

```text
8 г
110 мл
95°C
8 / 10 / 15 секунд
```

являются **примерами поведения системы**, если прямо не указано иное.

Перед наполнением production database определить фактические рекомендации по китайским источникам.

Это критически важно.

---

# 130. Финальный ожидаемый результат

После выполнения задачи repository должен содержать полностью работающий Tea Guide:

- исходный код;
- content;
- brewing recipes;
- sources;
- тесты;
- PWA;
- SEO;
- GitHub Actions;
- автоматический GitHub Pages deployment;
- документацию.

Сайт должен ощущаться прежде всего как:

**«Я достал чай — открыл Tea Guide — через несколько секунд уже правильно завариваю его проливами».**

Не как:

**«Я открыл ещё одну Википедию про чай».**

# 132. Не сокращать scope молча

Если определённая web API функциональность имеет browser limitations:

например:

- vibration;
- Wake Lock;
- PWA installation;

не удаляй feature целиком.

Реализуй progressive enhancement и graceful fallback.

---

# 133. Quality bar

Не считать:

```text
"страница открывается"
```

достаточным результатом.

Проверять интерфейс как реальный пользователь.

Особое внимание уделить:

- одной руке на телефоне;
- чайным мокрым пальцам;
- большим кнопкам;
- быстрому чтению;
- минимальному количеству действий;
- состоянию после блокировки телефона;
- состоянию после возвращения;
- случайному refresh;
- плохому интернету.

---

# 134. Финальная проверка основного сценария

Перед завершением проекта вручную пройти:

```text
Открываю сайт.

Нахожу Да Хун Пао.

С первого экрана понимаю, где его заваривать.

Нажимаю «Заварить проливами».

Выбираю гайвань 120 мл.

Вижу точную рекомендацию по граммовке.

Вижу температуру.

Начинаю чаепитие.

Если нужна промывка — сайт ведёт через неё.

Нажимаю первый пролив.

Ухожу из браузера.

Возвращаюсь.

Таймер правильный.

Получаю сигнал.

Сливаю чай.

Сайт уже знает время следующего пролива.

Я нажимаю одну большую кнопку.

Повторяю до конца.
```

Если этот flow не ощущается чрезвычайно простым — продолжить UX-работу.

---

# 135. Главное правило продукта

При принятии любых неоднозначных решений используй следующий приоритет:

```text
1. Удобство таймера
2. Достоверность рецепта
3. Скорость доступа к рецепту
4. Mobile UX
5. Читаемость
6. SEO
7. Энциклопедическая полнота
8. Декоративность
```

Нельзя жертвовать первыми пунктами ради последних.

**Tea Guide прежде всего должен стать лучшим удобным инструментом для заваривания конкретного китайского чая проливами.**
